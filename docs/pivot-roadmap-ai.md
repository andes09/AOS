# Omada: roadmap-AI direction

**Status**: current product direction as of the 2026-07-13 pivot.

## What this product is now

Omada takes a person's idea — hobby project, startup, or something they're
learning — and turns it into a structured roadmap: milestones and tasks they
can actually work from, generated by an LLM and editable afterward.

This replaces the prior direction (internally "AgileOS"): a Jira-connected
sprint-planning copilot for existing engineering teams. That product and its
Jira integration, ticket sync, and Scope Cop scope-checking are gone (see
`docs/archive/`). Omada is single-user-oriented, GitHub-connected instead of
Jira-connected, and starts from a conversation rather than an existing
backlog.

## The onboarding → roadmap flow

```
github_connect → profile → purpose → idea_chat → done → roadmap
   (skippable)                          (AI interview)
```

1. **GitHub connect** — optional OAuth link, skippable.
2. **Profile** — name + phone.
3. **Purpose** — a fixed 3-way choice: `hobby | startup | learning`. This is
   not free text; it's the steering input for step 4 (see below).
4. **Idea chat** — an AI interview (SSE-streamed) that asks purpose-shaped
   questions and extracts a structured `ProjectBrief` as it goes.
5. **Roadmap generation** — once onboarding completes, the brief feeds an LLM
   call that produces `RoadmapProject { milestones[] { tasks[] } }`. The user
   can regenerate the whole plan, regenerate a single milestone, or edit
   tasks (retitle, reschedule, reorder, check off) with every edit applied
   optimistically.

Full frontend integration contracts for each half of this flow:
`docs/onboarding-v2-frontend-integration.md` and
`docs/roadmap-frontend-integration.md`.

## Key architectural decisions

**Purpose steering.** `purpose` is a closed enum, not free text, specifically
so it can drive the system prompt server-side (`onboarding_v2.py`) without
the frontend needing to know or reconstruct the prompting logic. A hobby
project gets asked about fun and spare time; a startup gets asked about
market and MVP scope; a learning project gets asked about skill goals. The
frontend's only job is to render three buttons and send the enum value.

**Headless pattern.** Both onboarding and roadmap ship as a "headless" layer
— a framework-agnostic API client plus React Query hooks
(`apps/web/src/features/onboarding-v2/`, `apps/web/src/features/roadmap/`)
— separate from any reference UI. The hooks own auth (Clerk bearer token),
error parsing, SSE streaming, optimistic updates, and rollback. Any UI built
against them renders from hook state and never calls `fetch` directly. This
let the actual product UI (roadmap page, onboarding page) be built or
rebuilt without touching backend-adjacent plumbing, and lets that plumbing
be tested once instead of per-UI.

**Derived-state contracts.** Each flow exposes one discriminated-union state
object (`state.status`: `loading | empty | generating | ready | error` for
roadmap; `state.currentStep` for onboarding) that the UI switches on
exhaustively, instead of ad-hoc booleans. The shape of that state
(`types.ts` in each feature folder) is kept in lockstep with the backend by
tests (`apps/api/tests/test_roadmap.py`, `test_onboarding_v2.py`) — the
contract is enforced in CI, not maintained by convention.

## Where things stand

- Onboarding v2 and roadmap generation/editing are built and merged to
  `main`.
- Feature flags (`apps/api/config/features/`): `roadmap_generation` and
  `planner` are on everywhere; `roadmap_chat` is on in local/dev, off in
  production pending rollout.
- Outstanding: production ops (Groq/Anthropic/GitHub keys in Railway).
